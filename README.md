# SecureVault - Zero-Knowledge Encrypted Notes Application

SecureVault is a secure, full-stack personal notes application. It implements **Zero-Knowledge double-layer encryption** using AES-256-GCM. 

* **Layer 1 (Client-Side)**: The note body is encrypted in the browser using the Web Crypto API. The server never receives or handles the plaintext note body.
* **Layer 2 (Server-Side)**: The server wraps the browser's ciphertext in a second layer of AES-256-GCM before saving it to an SQLite database.

## Getting Started

### Prerequisites
* [Node.js](https://nodejs.org/) (v18.0.0 or higher recommended)
* `npm` (packaged with Node.js)

### Project Setup

#### 1. Backend Server Setup
1. Open a terminal and navigate to the `backend/` directory:
   ```bash
   cd backend
   ```
2. Install the backend dependencies:
   ```bash
   npm install
   ```
3. Create a `.env` file by copying the example template:
   ```bash
   cp .env.example .env
   ```
4. Open the newly created `.env` file and review the variables. The backend is configured to run on port `5002`.
5. Start the backend development server:
   ```bash
   npm run dev
   ```
   *Note: On startup, the SQLite database is automatically created as `database.sqlite` in the backend root and the required tables are initialized.*

#### 2. Frontend Client Setup
1. Open a new terminal window/tab and navigate to the `frontend/` directory:
   ```bash
   cd frontend
   ```
2. Install the frontend dependencies:
   ```bash
   npm install
   ```
3. Start the Vite React development server (runs on `http://localhost:5173` by default):
   ```bash
   npm run dev
   ```
4. Open your browser and navigate to `http://localhost:5173`.

## Part 3 — Encryption Write-Up

### 1. Why AES-256-GCM?
AES-256-GCM (Galois/Counter Mode) is an **Authenticated Encryption with Associated Data (AEAD)** cipher. Unlike AES-CBC (Cipher Block Chaining), which only provides **confidentiality**, GCM provides both **confidentiality and integrity/authenticity** in a single, parallelizable operation. 

Without GCM's built-in authentication, ciphers like CBC are vulnerable to **bit-flipping attacks** (where an attacker modifies ciphertext to selectively alter decrypted bytes) and **padding oracle attacks** (like Lucky Thirteen) which leak plaintext details. GCM prevents this by appending an authentication tag, ensuring that any ciphertext tampering is detected before decryption occurs.

### 2. How is the IV handled?
The **Initialization Vector (IV)** ensures that identical plaintexts encrypt to different ciphertexts. 
* **Client-Side**: A unique 12-byte (96-bit) IV is generated using `window.crypto.getRandomValues()`. It is encoded to Base64 and sent to the server.
* **Server-Side**: A separate 12-byte IV is generated via Node's `crypto.randomBytes(12)` for the second encryption layer.
* Both IVs are stored alongside the ciphertexts in the database (`iv` and `clientIv` columns).
* **If an IV is reused** with the same key, GCM's counter-mode design degenerates into a **two-time pad**. An attacker intercepting two ciphertexts sharing an IV can XOR them to eliminate the key and extract plaintext relationships. Furthermore, IV reuse in GCM leaks the internal hash key (GHASH key), allowing attackers to forge arbitrary ciphertext blocks.

### 3. What does the auth tag protect?
The **authentication tag** (a 16-byte tag generated by GCM's GHASH function) protects the **integrity** of the ciphertext. It acts as a cryptographic checksum confirming that the encrypted payload has not been modified in transit or database storage. 

It defends against **active tampering and injection attacks**. If an attacker tampers with the ciphertext, the computed auth tag will not match the stored tag, causing the decryption function (`decipher.final()` or `subtle.decrypt`) to throw an error and discard the payload, preventing the leakage of corrupted plaintexts or structural side-channel data.

### 4. One known weakness & fix
* **Weakness**: We send note titles in plaintext from the client to the server, and although they are encrypted *on the server* before database storage, the server is still aware of the notes' metadata (titles) in transit.
* **Fix/Upgraded Architecture**: Initially, sending raw passwords over the network presented a risk if the server itself was compromised. To address this, we implemented a **Zero-Knowledge Dual-Key Derivation** scheme. The browser inputs the user's password and derives a 512-bit key using PBKDF2 (100,000 iterations, with the user's email hashed as salt). 
  * The first 256 bits are imported locally as a non-extractable `encryptionKey` (AES-GCM) for note body encryption. 
  * The remaining 256 bits are converted into a hex string (`authKey`) and sent as the password value to `/auth/login` and `/auth/register`. 
  
  The server only ever sees the `authKey`, keeping the actual master password and decryption key entirely hidden from the host. To fix the title metadata leakage given more time, we would extend the client-side AES-GCM encryption to envelope the note title as well, transmitting only double-encrypted opaque structures.
